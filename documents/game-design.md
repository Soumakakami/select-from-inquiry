# ゲーム仕様

## コンセプト

- プレイヤーは架空のゲーム会社「株式会社ノクトゲームス」のサーバーエンジニア。運営中の架空MMORPG『クロノリア・オンライン』のCSチームから調査依頼チケットが届く。
- 本番DB（参照専用レプリカという設定）にSQLを投げ、ログから事実を確かめて回答する。
- テーマは「ユーザーの言い分が正しいとは限らない。ログは嘘をつかない」。本人の操作ミス、仕様どおりの挙動、本物の不具合、不正アクセスが混ざっている。
- 条件：Web上で誰でも遊べること。インストール不要、サーバー不要。

## ゲームの流れ

**1日5件 × 20日 ＝ 100件**。1日の5件を片付けると、その日の結果が出て、翌日に新しい問い合わせ票が届く。

1. タイトル画面。はじめては「▶ 研修から始める」か「研修をスキップして出社する」を選ぶ。途中まで遊んでいれば「続きから（DAY n・#k）」（研修中なら「研修の続きから」）。DBの準備中は押せない。
2. 研修を選んだ場合は、DAY 1 の前に**研修**（3件、下記）。終わると修了証が出て、DAY 1 へ。
3. 端末の起動ログが流れ（クリックでスキップ可）、「DAY 1」のカットイン、先輩のあいさつ、最初のチケットが届く。
4. 問い合わせ票（チケット）を読む。受付日時（JST）、ユーザーの怒りゲージ、公開ID、ワールド、種別、本文、CS担当メモがある。
5. SQLコンソールでログを調べる。
6. 回答する：**調査結論**（4択）を選び、**根拠**（決め手になった値）を入力して送信。
7. 正解なら「解決」の印鑑が押され、ユーザーへの回答文、ユーザーの反応、解説、模範SQLが表示される。「次のチケットへ」で次が届く。
8. その日の5件が終わると「本日の業務を終える」→ **1日の結果画面**（退勤時刻、PERFECT数、5件を1行ずつ判を押す演出、その日の評価 S / A / B / C）。
9. 「翌日へ」で時計が 10:00 に戻り、「DAY n」のカットインと先輩のあいさつのあと、次の5件が届く。
10. DAY 20 が終わると**最終結果画面**（20日分を1行ずつ、合計点、称号）。

### 研修（チュートリアル）

DAY 1 の前に、Kさんのレクチャーを受けながら固定の簡単な問い合わせを3件解く。経験者はスキップできる。

| # | チケット | 覚えること | 正解 |
|---|---|---|---|
| 研修1 | キャラが消えた？ | SQLの実行、公開ID → user_id、usr_characters を user_id で絞る、セルのダブルクリックで根拠を入れる | 消えていない（根拠は character_id） |
| 研修2 | ポーションが減った | 自分で書く、log_ テーブルを ORDER BY created_at DESC で時系列に読む、mst_items と JOIN して名前を付ける | 本人が使った（根拠は USE の log_id） |
| 研修3 | ログインできない | ［運用メモ］を開く、AND と date(created_at) で日付を絞る、ユーザーの言い分とログが食い違ったらログを信じる | その日もログインできている（根拠はその日の SUCCESS の log_id） |

- 問い合わせ票の上に**研修ノート**が出る。ステップの一覧（済んだものにチェック）、いまのステップのKさんの説明、例のSQL（「例をエディタに書き写す」ボタン）。同じ説明は会話ウィンドウにも出る。
- いま触ってほしい場所（実行ボタン、エディタ、運用メモのタブ、回答用紙）が黄色く点滅する。
- ステップは、SQLを実行した結果で自動的に進む（例：結果に、そのユーザーの user_id の行が出たら「user_id を調べる」が済む）。経験者が1本のSQLでまとめて調べれば、いくつも一度に進む。回答して正解するか［先輩に聞く］を使えば、その研修は修了。
- 研修中は**点数も時計も動かない**。差し戻しやヒントも減点なし。更新系のSQLを流しても始末書は出ず、Kさんが注意するだけ。「仕様です」ボタンは出ない。
- 3件終わると**研修修了証**（覚えたことの一覧）が出て、「DAY 1 へ出社する」。DAY 1 の朝は「研修おつかれ。ここからが本番だ」から始まる。
- スキップは、タイトル画面の「研修をスキップして出社する」か、研修ノートの「研修をスキップ」（2回押し）。
- 本番の途中でも、タイトル画面の「研修を受け直す」で研修だけやり直せる。本番の進み具合はそのままで、終わると元のチケットに戻る。
- 研修の3件は、本番の100件とは別のユーザーから、DBの実データで毎回同じものを選ぶ（`src/casegen.js` の `training()`）。

### 日とチケットの順番

- 最初の1件は、チュートリアル代わりの『キャラ消失』。あとは**難しさの順**（1 → 2 → 3）に並び、同じ難しさの中では新しく始めるたびに**ランダム**。前から5件ずつがその日の分になる。
- 難しさ1は42件（DAY 1〜9ごろ）、2は41件（DAY 9〜17ごろ）、3は17件（DAY 17〜20）。難しさが上がる日は、先輩が朝に「今日からは〜」と予告する。
- 上部のバーにはその日の5件だけが出る（#1〜#5）。まだ届いていないチケットは「？？？」。前のチケットにはいつでも戻れる。
- 最初のチケットだけ、エディタに「まずはユーザーを探してみよう」というSQLの例が入る。
- DBは 11/13 10:00 時点のスナップショットのまま。各日のチケットは、それまでに届いて溜まっていた問い合わせ（受付日時は 10/21〜11/13）を1日5件ずつ処理していく、という設定。
- 問い合わせ票100件のうち、元の7件は手作り、残りの93件は DB の実データから自動で作る（[cases.md](cases.md) の「自動生成の問い合わせ」）。

### 回答方式をこうした理由

自由記述の返信文は自動で採点できないため、「結論の選択」＋「根拠の値」の2つで判定する。
結論だけだと問い合わせ文から推測できてしまうので、根拠（log_id、取引ID、公開IDなど）を入力させて、実際にログを見つけたかを確かめる。

誤答時は、どちらが違うかだけを先輩のセリフで伝える。

- 両方違う：「結論も根拠も、もう一度ログを見直してみて」
- 結論だけ違う：「根拠に挙げた値は合ってる。でも、そこから言える結論は別じゃない？」
- 根拠だけ違う：「結論はいい線。でも根拠の値が違う。どのログが決め手？」

## 採点

| 項目 | 点数 |
|---|---|
| 1件あたりの基本点 | 100 |
| 差し戻し（誤答）1回 | −25 |
| ヒント1つ | −10（各ケース3段階まで） |
| 解決時の下限 | 20 |
| 先輩に聞く（ギブアップ） | そのケースは0点。解説が見られる |
| 始末書1枚 | 合計から −15 |
| コンボボーナス | 誤答・ヒントなし（PERFECT）で連続解決すると、2件目から +10、3件目 +20 …、6件目以降は +50 で頭打ち。日をまたいでも続く。誤答・先輩に聞く・「仕様です」・裏ルートでリセット |
| 「仕様です」で即答（当たり） | そのケースは 60 点。**1日1回まで** |
| 「仕様です」で即答（外れ＝炎上） | 合計から −50。ケースは未解決のまま |
| 裏ルート（直接UPDATE） | そのケースは 80 点 |
| 始末書をゴミ箱に入れる | その始末書を取り消し（+15 が戻る） |

満点は 14,850（基本点 10,000 ＋ 100件連続 PERFECT のコンボ 4,850）。称号は満点に対する割合で決まる。

| 割合 | 称号 |
|---|---|
| 90%〜 | ログの声が聞こえる人 |
| 75%〜 | 頼れるサーバーエンジニア |
| 55%〜 | 一人前の調査担当 |
| 35%〜 | 見習いエンジニア |
| 〜35% | 研修やり直し |

**1日の評価**はその日の5件の得点（コンボ込み）で決まる：S 560点以上、A 450点以上、B 320点以上、C それ未満。

始末書が3枚以上なら、称号に「（始末書の常連）」が付く。
最終結果画面には定時退社した日数、最大コンボ、始末書の枚数などのバッジと、20日分の表（解決数、PERFECT数、退勤時刻、評価、点）が出る。
「結果をコピー」で、SNS向けの1行（点数、PERFECT件数、毎日の評価の並び、称号、最大コンボ、始末書枚数）をコピーできる。

### ゲーム内時計

毎朝 10:00 出社。操作するたびに時計が進む（得点には影響しない）。定時の 18:00 を過ぎると HUD の時計が赤くなる。HUD には「DAY n」と時刻が出る。

| 操作 | 進む時間 |
|---|---|
| SQLを実行（未解決のチケットで） | 2分 |
| ヒント | 3分 |
| 差し戻し | 8分 |
| 解決 | 10分 |
| 先輩に聞く | 15分 |

## 給料と購買部

点数（称号と毎日の評価に使う）とは別に、1日の終わりに**給料（G）**が出る。給料で道具や消耗品を買うと、翌日からの調査が楽になる。買い物をしても点数や称号は減らない。

### 給料

1日の結果画面に**給与明細**が出る。最終日は最終結果画面の時点で支給する。

| 内訳 | 金額 |
|---|---|
| 基本給 | その日の得点 × 1 G |
| 定時退社手当 | +50 G |
| 皆勤賞（その日の5件すべて解決） | +50 G |
| 評価手当 | S +150 / A +80 / B +30 / C 0 |
| 減給（始末書） | 1枚につき −30 G（その日にもらって、ゴミ箱に入らなかった分） |
| 減給（炎上） | 1回につき −50 G |

研修を修了すると、初任給として 300 G。研修中は給料が出ない。

### 買える場所

- **購買部**は1か所だけ。入口は2つで、品ぞろえも値段も同じ。
  - HUD 右上の**［購買部］ボタン**（赤白のひさし付きの緑の看板。所持金もここに出る）から、業務中いつでも。閉じると仕事に戻る。
  - 1日の結果画面の「購買部に寄る」から。閉じるボタンは「翌日へ」と「本日の結果に戻る」。
- 店番は購買部のおばちゃん。売り場は**タブ**で分かれる：調査ツール（最初に開く）／消耗品／机の飾り／カセット。タブには、いま買える品の数が出る。
- 毎日1品が「本日の特価」（30%引き）。
- 前にのぞいたあとに新しい品が入荷すると、HUD の［購買部］と結果画面の「購買部に寄る」に **NEW** が点滅し、店の中ではその品に「新入荷」の札が付く。おばちゃんも入荷した品をすすめてくる。
- 道具のカードには「使う場所」（問い合わせ票、結果の表、資料の［運用メモ］など）が書いてある。道具は買ったその場から使える。

### お金の目安

1日 350〜850 G ほど、20日で 7,000〜15,000 G ほど。道具をすべて買うと 10,000 G、飾りとカセットも合わせると約 13,200 G なので、どの道具から買うかを選ぶことになる。上手な人ほど多く買える。

## 遊びの演出

- **登場人物**：ドット絵の4人が右下の会話ウィンドウ（文字送り、クリックで送る／閉じる）で話しかけてくる。
  - Kさん（先輩エンジニア）：あいさつ、ヒント、差し戻し時の指摘、解決時のほめ言葉
  - Uさん（CSチーム）：新しいチケットが届いたときの依頼（CS担当メモの内容）
  - Hさん（インフラ担当）：重いクエリへの苦情
  - 部長：始末書
- **チケットの着信**：電話のベル → 「INCOMING TICKET」のカットイン → 問い合わせ票がプリンターから印字されて出てくる。
- **ユーザーの怒りゲージ**：問い合わせごとに初期値（2〜5）があり、差し戻すたびに上がる。解決すると「鎮火」。得点には影響しない。
- **解決**：画面フラッシュ、「CASE CLOSED」（ノーミスなら「PERFECT!」）のカットイン、印鑑の周りに紙吹雪、スコアの横に「+100」、スコアのカウントアップ。コンボ中は「◯ COMBO」のカットインも出る。
- **差し戻し**：赤いフラッシュ、問い合わせ票が激しく揺れ、「差し戻し」のカットイン。
- **始末書**：SELECT / WITH / EXPLAIN / VALUES / `PRAGMA table_info` 以外を実行しようとすると、実行を止めて始末書（−15）。赤い警報ランプ、画面全体の揺れ、カットイン、部長のひとこと。DELETE、UPDATE、DROP などコマンドごとにメッセージが変わる。
- **重いクエリ**：結果が2,000行以上になると、インフラ担当が話しかけてくる（減点なし）。繰り返すと反応が悪化する（下の「ゲームだからいいよね」を参照）。件数は20万行で数えるのを打ち切る。
- **日時**：DBの日時も問い合わせもすべて日本時間（JST）。初心者がタイムゾーンでつまずかないよう、時差の要素は入れていない。画面右の「運用メモ」タブに明記している。
- **MySQLとの違い**：MySQLの書き方（`DATE_ADD` や `INTERVAL` など）でエラーになったら、SQLiteでの書き方をヒントとして出す。`CONVERT_TZ()`、`NOW()` は独自関数として使える。

- **サウンド**：夜の運用デスクに合う落ち着いたローファイBGMと、SQL実行、印鑑（解決・差戻）、ヒント、始末書の警報、結果発表のファンファーレなどの効果音。HUD右上の「BGM」「SE」で個別にオン／オフできる。詳しくは [architecture.md](architecture.md) の「サウンド」。

## 現実ではやっちゃいけないけど、ゲームだからいいよね

実務経験者から「嫌な思い出がある」という声があったので、現場で本当はやりたかった（でも絶対にやってはいけない）ことを、ゲームの中でだけ叶える。どれも必ず「※現実では〜」の一言を添えて、間違ったことを覚えないようにする。

## 画面構成

デスクトップでは3列。

| 左 | 中央 | 右 |
|---|---|---|
| **木の机**：問い合わせ票（連続帳票）と、クリップ付きの回答用紙 | **レトロなモニター**：ベージュの筐体の中の暗い画面に、SQLエディタ（構文ハイライト）と結果テーブル | **青いバインダー**：「テーブル定義」と「運用メモ」（付箋）のインデックスタブ |

- 上部のHUDに、その日のチケットの進み具合（5つのチップ、新着は NEW。全件終わると「本日の業務を終える」）、ゲーム内時刻、スコア、コンボ（2以上のとき）、始末書の枚数、**［購買部］ボタン（所持金つき）**、BGM／効果音の切り替え。時計・コイン・炎・書類・お店のドット絵アイコン付き。
- 幅1180px以下では2列、760px以下では1列に縦積み。

### 操作

- Ctrl+Enter（Macは⌘+Enter）で実行。範囲選択していれば、その部分だけ実行。
- 複数のSQLを `;` 区切りで書くと、結果を縦に並べて表示する。
- テーブル定義のテーブル名を押すと `SELECT * FROM … LIMIT 20;` がエディタに入る。列名を押すとカーソル位置に挿入。
- 結果のセルをダブルクリックすると、回答の根拠欄に値が入る。
- 結果は1,000行まで表示（件数は全件数える）。

### デザイン

- **画面全体をドット絵のUIに寄せる**。暗くなりすぎないよう、夕方のオフィスのような明るめの藍色（2×2のディザ模様）を地にする。
- 3つのエリアを「物」として描き分け、どこで何をするかを見た目で分かるようにする：
  - 左は木目の机。問い合わせ票は連続帳票（左右に送り穴とミシン目、耳だけ緑。本文の下は無地で読みやすく）、回答用紙はクリップ付きの紙。選択肢・入力欄・ヒント（付箋色）も紙の上の部品として描く。
  - 中央はベージュの筐体のモニター（右下に電源ランプ）。暗いのは画面の中だけで、走査線とビネットも画面の中にだけかける。
  - 右は青いバインダー（リング付き）。中の紙にテーブル定義、運用メモは黄色の付箋（マスキングテープ付き）。
- 枠や部品はドット絵の作法で描く：角を1ドット欠いた「ドットの角丸」（`clip-path`）、立体感は内側の明暗の影（左上が明るく右下が暗い）、ぼかした影やグラデーションは使わない。
- モーダルと会話ウィンドウはRPGのメッセージ枠風（白い太枠＋黒い内枠、話している間はアイコンが揺れ、話し終わると ▼ が点滅）。
- 印鑑は角印（四角い二重枠）。ラジオボタン、スクロールバー、チェックマーク、ランプもすべて四角いドット。
- アニメーションは `steps()` でコマ送りにし、なめらかに動かさない（印鑑、カットイン、紙吹雪、得点、印字）。カットインの帯の上下は市松模様のディザ。
- タイトル画面は夕暮れの街のドット絵（空の色の帯、星と月、窓の明かりがまたたくビル街、中央に看板の光る会社のビル）に、立体的な影のロゴ（ときどきグリッチ）。登場人物とルールはウィンドウにまとめる。背景は `fx.js` の `skyline()` がSVGで描く（画像ファイルなし）。
- 学習ソフトに見えないよう、正解・誤答・始末書などの節目にはカットインや画面効果で手応えを返す。調べている最中（SQLを書いて結果を読む部分）は邪魔をしない。
- `prefers-reduced-motion` のときは揺れ・紙吹雪・走査線などを止める。
- **フォントはすべてドット**：
  - 日本語と本文・コード：**DotGothic16**。ドットがぼやけないよう、16px の倍数（16 / 32 / 48 / 64px）だけで使う。本文・表・SQLエディタはすべて 16px、行の高さは 24px。
  - 英字のラベルと数字：**Press Start 2P**（SCORE、COMBO、READ ONLY、カットインの英語、スコアの数字など）。8px の倍数だけで使う。日本語の字形がないので、日本語を含む文字列には使わない。
  - `-webkit-font-smoothing: none` で、mac でもドットのふちをにじませない。

## 進行の保存

- 進み具合（所持金・生涯年収・使った額、持っている消耗品と道具、使い中の効果、選んだカセット、付箋メモ、研修中か本番か、研修の各ステップ、今が何日目か、各日の退勤時刻と得点）、チケットの順番、100件それぞれの成績、コンボ、ゲーム内時計、「仕様です」を使った日、エディタの下書きを `localStorage`（キー `logs-dont-lie:v1`）に保存。リロードしても続きから遊べる。
- 保存データは100件の問い合わせ票がそろってから読む。7件だった頃の保存データは形が合わないので、最初からになる。研修が入る前の保存データは、そのまま本番の続きとして読む（研修は「研修を受け直す」で受けられる）。
- 読み込み時に古い保存データを直す：実行履歴は削除、下書きの古いテーブル名（`users` など）は新しい名前（`usr_users` など）に置き換える。
- DB自体は保存しない。シード固定で毎回同じデータを作り直すため。
